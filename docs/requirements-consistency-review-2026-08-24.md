# Metric Pulse Platform 需求与技术方案一致性回检

- 回检日期：2026-08-24
- 基线：需求文档 V2.4、技术方案 V2.4、系统/应用设计 v1.4
- 范围：金标边界、P0-3 状态语义、P0-2 吞吐与恢复、P0-4 异常审核、直链优先路由、验收口径

## 结论

本轮文档回检后，未发现会阻断按 `P0-3 → P0-2 → P0-4` 实施的未决需求冲突。已发现的口径冲突均已统一为下表中的决策。

截至 2026-08-24 本轮实施结束，下表决策已完成代码、迁移、API/UI 和回归落地。验收报告中历史已通过结果仅保留为当时管线/Excel 重建事实，不作为采集准确率证据。

## 冲突回检表

| 主题 | 原冲突 | 统一后的决策 | 状态 |
| --- | --- | --- | --- |
| 金标使用 | 历史金标可验收，但现有 `gold collector` 把它带入平台运行路径 | 平台在无金标权限的环境中运行；完成后由独立验收器比较 | 已完成生产边界移除与自动扫描 |
| 执行成功与业务完成 | `SUCCEEDED` 可包含全空值，又被用作进度/成功口径 | execution/resolution/review 正交建模；`SUCCEEDED + null` 不计入 `RESOLVED` | 已解决，纳入 P0-3 |
| 模型批处理 | 先前方案把多行模型批处理当作吞吐优化 | 禁止模型批处理和并发；一次请求只能有一个 RowContract，OMLX 全局并发固定为 1 | 已解决，纳入 P0-2 硬约束 |
| 模型调用次数 | 先前方案提议 Tier 0/1/2 减少模型次数 | 只使用 `Qwen3.8-27B-6bit`；所有行固定串行执行候选综合和独立证据复核两次请求，结构化来源也不跳过 | 已解决，纳入 P0-2 硬约束 |
| 采集直链与搜索顺序 | 旧实现每行先搜索，再把工作簿直链放到候选末尾，可能绕过明确官方数据 | 有采集直链时先规范化、获取、解析并按 RowContract 唯一匹配；仅在无直链、失败、无数据或歧义时逐行搜索降级 | 已确认，ADR-0006 取代旧逐行必搜口径 |
| 来源复用与行证据 | 先前方案提议相同查询或会话跨行复用 | 只复用不变 SourceSnapshot/结构化索引；每行重新生成证据切片、提示词、两次模型请求、校验和提交；不复用搜索响应、候选、结论或会话 | 已解决，纳入 P0-2 硬约束 |
| `preserve` 与金标 | 历史金标中“未变”曾被写成生产 `preserve` 选择依据 | `preserve` 只由当次业务配置/用户授权决定；生产系统不知道也不假设金标存在 | 已解决，并入金标前置门禁 |
| 正式导出与人工全审 | 旧口径可被理解为所有结果必须逐行人工批准 | 导出始终受审核门禁，但低风险确定性结果可由版本化 ReviewPolicy 产生 `AUTO_APPROVED`，并受抽样/熔断约束 | 已解决，纳入 P0-4 |
| 无法填值与完成审核 | 保持空值会永久阻塞导出，随意 `SKIPPED` 又会掩盖必需缺口 | 调查充分后用 `CONFIRMED_UNRESOLVED` 完成审核并生成未解决报告；`SKIPPED` 只适用于配置明确的可选项 | 已解决，纳入 P0-4 |
| 当前实现与目标架构 | 旧描述将 SQLite eager 和 PostgreSQL/Celery 目标路径混为已验收事实 | 文档分开“2026-08-24 当前本地运行”与“目标生产架构”，验收报告不预宣布 P0 已完成 | 已解决 |

## 实施回检

1. 生产包、环境示例和 Compose 已移除金标 collector/路径/模式，测试目录使用外部假采集器，边界扫描已通过。
2. 数据库已实现 execution/resolution/review 正交状态、保守迁移、独立统计、API/UI 和导出门禁。
3. 已建立 RowSearchAttempt、ModelCall、SourceSnapshot、UnitSourceLink、URL/内容缓存、lease 恢复和 `next_attempt_at` 退避；ADR-0006 新增的 SourceAcquisitionAttempt、直链优先、持久化结构化索引和搜索降级尚待本轮代码落地。
4. OMLX 通过进程内异步锁与跨进程文件锁共同保证全局单通道；固定模型 ID 和最大 in-flight=1 回归已通过。
5. 结构化提取已改为候选证据，不再提前返回；生产提交硬门禁将由“一次逐行搜索”改为“一条成功的 DIRECT_LINK/SEARCH_FALLBACK 采集路由”，并继续要求严格 `SYNTHESIZE → VERIFY` 两次请求。
6. 已建立不可变 ReviewPolicy 版本、自动通过抽样/熔断、批量 preview/commit 快照、`CONFIRMED_UNRESOLVED` 和 JSON 未解决报告。

## 实施门禁

1. 用户审阅本回检与 ADR-0005。
2. 完成金标隔离前置门禁。
3. 只开始 P0-3；通过状态真值表、迁移、API/UI 和导出验收后才开始 P0-2。
4. P0-2 通过“每行独立采集路由、必要时逐行搜索降级、每行固定两次 Qwen、全局并发 1、无模型批次/跨行会话”契约检查，以及 URL/内容去重、等价性、恢复和资源指标验收后才开始 P0-4。

## ADR-0006 增量冲突回检

1. “直链优先”与“每行都搜索”的旧要求直接冲突，已明确由用户的新业务要求和 ADR-0006 取代旧要求；搜索仍逐行隔离，但变为条件降级。
2. “相同来源复用上下文”不等于“模型复用会话”：只复用不可变原文、解析索引和当前行有界切片，每行保持两个全新独立模型请求，因此与禁止模型批处理、避免跨行误解兼容。
3. 直链确定性匹配不会跳过模型。唯一结构化匹配仍作为本行证据完成 `SYNTHESIZE` 与 `VERIFY`，因此与固定双阶段质量契约不冲突。
4. OMLX 前缀缓存是机会性加速，不作为业务缓存或结果复用；缓存开关不影响结果，因此与行隔离和可复现性兼容。
5. 金标仍只属于外部测试/验收。历史影响扫描依据生产审计中的输入链接、选中来源和确定性匹配差异，不读取金标，因此不改变生产边界。
6. 当前任务必须在自然完成在途单元后进入 `PAUSED` 才重启服务；文档修改不触发热重载，不影响当前执行。

结论：除已由 ADR-0006 显式取代的“每行固定先搜索”外，未发现与状态语义、双阶段模型、OMLX 并发 1、审核门禁或金标隔离的新冲突。代码实施门禁为：先完成路由审计与契约测试，再迁移副本、回归和缓存基准，最后升级本地服务并恢复任务。
5. P0-4 通过策略审计、抽样熔断、批量冲突和未解决报告验收后，再继续后续整表与生产化工作。
